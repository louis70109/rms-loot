# ADR 0007：用 GitHub Actions 排程做網站偵測，不另外用監控服務

- 狀態：已接受
- 日期：2026-11-17

## 背景

2026-11-16 的部署失敗（volume 所在主機不可達，之後又出現 Dockerfile 漏檔案）讓網站斷線好幾個小時。系統沒有主動偵測，只能等有人打開網站時才發現。需要一個能主動發現的機制。

## 決定

1. `.github/workflows/uptime.yml` 每 12 小時（UTC 00:17、12:17）檢查 `https://rms-loot-nj.fly.dev/healthz`，也可以用 `workflow_dispatch` 手動執行。
2. 成功條件：HTTP 200 且內容是 `ok`。
3. 機器閒置會休眠，第一次請求可能很慢，所以失敗前會重試 4 次，每次間隔 30 秒、單次逾時 90 秒。
4. 失敗時這次執行變紅，GitHub 會寄通知給 repo 的 watcher。不需要任何 secret。

## 為什麼是 12 小時

- 每次檢查都會喚醒休眠的機器，檢查越頻繁，機器實際運作的時間越長，費用也越高。
- 網站是個人使用的工具，半天發現一次問題可以接受。
- 若需要更快，可以改 cron，但要一併考慮費用。

## 考慮過的替代方案

- **外部監控服務（UptimeRobot 等）**：功能更多，但多一個帳號與服務。目前只需要知道網站是否活著。
- **每小時檢查**：最早的版本，後來改成 12 小時，理由見上面。
- **fly 內建的健康檢查**：只能看到機器狀態，看不到錯誤通知，也不會寄信給人。

## 後果

- 正面：沒有額外的服務與 secret；失敗會通知。
- 負面：只檢查 `/healthz`，能發現整站掛掉或啟動失敗，但發現不了單一頁面壞掉或資料錯誤。
- 負面：檢查本身會喚醒機器，有一點費用。
- 注意：GitHub 的排程可能延遲幾分鐘，不保證準時。
